# Highly Capable Assistant AI — External Source & Tool Catalog

## Purpose

This catalog is a practical source map for building a **general-purpose, highly capable assistant AI** that can research, reason, verify, calculate, retrieve data, inspect files, interact with software, and handle domain-specific tasks.

The catalog expands the original 25 source/tool categories into their major sub-sources. Each entry includes a URL that an AI agent can programmatically or directly retrieve, plus an access note.

### Access labels

- **PUBLIC** — reachable without an account in ordinary use.
- **PUBLIC API** — machine-readable API available publicly, sometimes with rate limits.
- **KEY** — API is publicly documented but requires a free/paid key.
- **AUTH** — requires user/account authorization.
- **PAID** — normally requires a subscription/license.
- **HUMAN/EXPERT** — not an automated source; requires a person or expert workflow.
- **TOOL** — computation/software capability rather than an information source.

> Important: “fetchable” does not mean “legally reusable without restriction.” Respect robots.txt, API terms, copyright, licensing, rate limits, privacy rules, authentication, and source-specific policies.

# Recommended Architecture for a “Highly Capable Assistant AI”

A strong implementation should not treat this as one giant search box. Build distinct layers:

1. **Task decomposition** — split the user's request into research, calculation, retrieval, creation, and verification subtasks.
2. **Source discovery** — search broad sources first, then move toward domain-specific and primary sources.
3. **Source ranking** — prefer authoritative/primary evidence; use community sources for edge cases and practical experience.
4. **Retrieval** — fetch pages, PDFs, datasets, APIs, code, images, audio, and authorized user files.
5. **Normalization** — convert responses into structured text, JSON, tables, embeddings, or other internal representations.
6. **Reasoning** — combine evidence across sources rather than trusting a single result.
7. **Computation** — use Python, symbolic algebra, statistics, simulation, spreadsheets, GIS, or other suitable tools.
8. **Execution** — interact with authorized applications and APIs when the task requires an external action.
9. **Verification** — independently check calculations, source agreement, timestamps, assumptions, and contradictions.
10. **Evidence tracking** — preserve the exact source URL, retrieval time, relevant passage/data, and confidence for each important claim.
11. **Escalation** — request human/expert judgment when the problem is high-stakes, ambiguous, proprietary, or beyond automated validation.
12. **Output synthesis** — return the answer in the format the user actually needs: explanation, report, code, table, file, design, decision, or action.

# Minimum “Universal Assistant” Stack

If the goal is maximum generality while keeping the system manageable, the highest-leverage baseline is:

- Web search + direct URL fetching
- General web crawler/parser
- Wikipedia/MediaWiki API
- Crossref + OpenAlex + PubMed/NCBI
- Internet Archive + Library of Congress
- Government/legal APIs (e.g., Data.gov, GovInfo, Congress.gov, SEC)
- GitHub API + source-code retrieval
- OpenStreetMap + geographic datasets
- Weather + finance + economic-data APIs
- User file ingestion
- Cloud/email/calendar connectors with explicit authorization
- Python execution
- SQL/database access
- OCR + speech-to-text + vision
- Vector search + full-text retrieval
- Citation/provenance store
- Automated verification/test harness
- Human escalation path

# Design Principle

**Search is only the discovery layer.** A highly capable assistant should be able to move from discovery → authoritative evidence → structured retrieval → computation → execution → independent verification → cited synthesis.

That architecture is much closer to a general-purpose research-and-action system than a conventional chatbot.

# Architectural takeaway

The expanded catalog suggests five broad capability layers for a highly capable general-purpose assistant:

1. **Knowledge** — web, books, papers, laws, datasets, knowledge graphs, archives, scientific databases, and domain-specific repositories.
2. **Perception** — documents, images, audio, video, maps, and sensor data.
3. **Action** — browsers, APIs, code execution, software repositories, package registries, cloud systems, and automation interfaces.
4. **Verification** — standards, benchmarks, testing, provenance, security intelligence, citations, monitoring, and independent cross-checking.
5. **Identity and coordination** — OAuth, OpenID, MCP, OpenAPI, JSON Schema, ontologies, permissions, and service discovery.

A stronger general architecture is therefore:

**USER → TASK DECOMPOSITION → SOURCE/TOOL DISCOVERY → RETRIEVAL → REASONING → EXECUTION → TESTING → CROSS-VERIFICATION → PROVENANCE → RESULT**

The goal is not merely to give the AI more sources. It is to give it a connected ecosystem in which it can discover information, choose specialized tools, act on external systems under explicit permissions, test its own work, and preserve evidence for how the result was produced.
